## 二、最严重的 6 个问题 (按优先级)

按照审计的优先级排序:

1. **Continuity 原子事务是假事务** — 必须改成 commit journal
2. **CHAPTER_FINALIZED 事件可能重复发布** — 必须统一唯一发布者
3. **Agent 生命周期事件和业务语义事件边界混乱** — 必须命名空间分离
4. **Writer 流式输出没有节流草稿保存** — 刷新会丢正文
5. **D5 强制完整 Anchor 与 Anchor 阶段 2 才存在矛盾** — spec 内部逻辑冲突
6. **任务表状态太粗,缺少 attempt/resumePoint/phase** — 恢复不可靠

## 三、审计原文

### 1. "原子事务"设计与 PGlite 能力不匹配

文档多处要求 Continuity 在章节落地时原子写入章节、CHANGES、快照、角色出场次数等内容,但设计里又承认 PGlite 不支持显式事务,只能"顺序执行 + 失败 rollback"。这在技术上是不可靠的。

现在的设计是:

```typescript
await updateFile(...)
await insertChapterChange(...)
await saveSnapshot(...)
await updateAppearanceCounts(...)
```

如果第 2 步成功、第 3 步失败,或者页面在第 3 步前崩溃,就会出现:

- 章节已 final
- CHANGES 已写入
- 快照没更新
- 角色出场没更新

这会破坏长篇一致性。

**建议改法**: 不要把它叫"原子事务"。应该改成 提交日志 commit journal 或 两阶段落地状态。例如新增:

```
chapterCommits {
  id
  taskId
  chapterId
  status: 'preparing' | 'committing' | 'committed' | 'failed'
  currentStep
  payload
  createdAt
  updatedAt
}
```

落地前先写 commit 记录。每完成一步更新 currentStep。应用重启时扫描未完成 commit,继续补完或标记 pending_review。这是比"失败后反向删除"更稳的设计。

### 2. Orchestrator 和 Continuity 都发布 CHAPTER_FINALIZED,可能重复

设计里 Continuity 完成后应发布 CHAPTER_FINALIZED,这是 requirements 里的标准事件流。

但 Orchestrator.runMVP() 的伪代码里,在所有 step 完成后又主动发布了一次:

```typescript
await this.bus.publish({
  type: 'CHAPTER_FINALIZED',
  taskId: parentTask.id,
  payload: outputs
})
```

而 Continuity 本身也被定义为最终落地者,完成事务后发布最终事件。这个会造成重复 finalized 事件。

**建议改法**: 只能保留一个事件来源。推荐:

- Continuity 是唯一 CHAPTER_FINALIZED 发布者
- Orchestrator 只负责推进步骤,不发布业务最终事件
- Orchestrator 最多发布 PIPELINE_COMPLETED
- 不要和业务事件混用

---

### 3. BaseAgent 的 DONE 事件和语义事件边界混乱

设计里的 BaseAgent.execute() 会自动发布:

- WRITER_STARTED
- WRITER_DONE
- WRITER_FAILED

但需求里又定义了语义事件:

- DRAFT_READY
- CRITIQUED_READY
- TIME_VERIFIED
- CHAPTER_FINALIZED

这会导致两套事件体系并存。问题是:

- WRITER_DONE ≠ DRAFT_READY
- CRITIC_DONE ≠ CRITIQUED_READY
- CONTINUITY_DONE ≠ CHAPTER_FINALIZED

DONE 只是 Agent 函数结束,READY/FINALIZED 是业务结果可用。两者混用会让 UI 和恢复逻辑混乱。

**建议改法**: 明确区分:

```
// 生命周期事件 (运行时)
AGENT_STARTED
AGENT_FINISHED
AGENT_FAILED

// 业务语义事件
DRAFT_READY
CRITIQUED_READY
CHAPTER_FINALIZED
```

并且不要用 ${agentName}_DONE 作为业务判断依据。

---

### 4. MessageBus 同时承担通信、持久化、UI 订阅,职责过重

当前 MessageBus 设计包含:

- on()
- subscribeAll()
- publish()
- 判断流式 chunk
- 持久化 agent_messages
- 通知 UI
- 触发 Agent 订阅

这会让总线变成一个"万能对象"。设计文档也明确选择了 in-memory 总线 + DB 持久化模拟消息队列。问题是后面会很难测试,也很难做恢复回放。

**建议改法**: 拆成三层:

```
EventBus        // 只负责内存事件分发
EventStore      // 只负责 agent_messages 持久化
TaskRuntime     // 负责把事件转成 UI 状态
```

发布时:

```typescript
await eventStore.append(event)
eventBus.emit(event)
```

流式 chunk 可以只走 eventBus.emit(),不进入 eventStore。这样职责更清楚。

---

### 5. agent_messages.taskId 设计可能导致父任务事件查询不完整

agentMessages 表只有:

- taskId
- type
- payload
- createdAt

而 taskId 指向某一个 agent task。问题是 UI 通常订阅的是父任务,但 Writer、Critic、Continuity 可能各自有子任务 ID。这样查询父任务事件时,要么查不到子任务消息,要么必须递归查子任务。

**建议改法**: agent_messages 应该同时存:

- parentTaskId
- taskId
- agentName
- chapterId
- projectId

推荐结构:

```
agentMessages {
  id
  projectId
  parentTaskId
  taskId
  chapterId
  agentName
  type
  payload
  createdAt
}
```

这样 UI、恢复、日志、审计都更方便。

---

### 6. agent_tasks.status 状态粒度不够

现在状态只有: pending / running / done / failed / cancelled

这对于流式写作系统不够。

Writer 至少会经历:

- running streaming
- awaiting_changes_parse
- retrying
- done
- failed

Continuity 至少会经历:

- validating
- committing
- committed
- failed
- pending_review

如果只用 running/done/failed,恢复任务时不知道停在哪一步。

**建议改法**: 增加字段,不一定把所有状态塞进 status:

```
status: 'pending' | 'running' | 'done' | 'failed' | 'cancelled' | 'pending_review'
phase: 'streaming' | 'parsing' | 'validating' | 'committing' | 'waiting_user'
resumePoint: string
attempt: number
```

这样恢复逻辑才可靠。

---

### 7. Writer 流式输出没有可靠的草稿保存机制

设计中 Writer 的 chunk 只通过 bus in-memory 转发,不持久化,这是合理的,因为持久化每个 chunk 会让 DB 膨胀。

但问题是: 如果 Writer 已经输出了 2500 字,页面刷新或崩溃,由于 chunk 没持久化,草稿会丢。

**建议改法**: 不要持久化每个 chunk,但要做节流式草稿快照:

- 每 2 秒或每 500 字保存一次 tempDraft
- 保存到 agentTasks.output.tempDraft 或 chapter.metadata.draftBuffer
- 最终完成后再清理

这样既不会 DB 膨胀,也不会丢长文本。

### 8. D5 前置条件和 Anchor 分期存在设计矛盾

requirements 规定章节生成前必须满足:

- ≥1 个 L1 角色,有完整 Anchor 档案
- ≥1 条世界观硬约束
- 已配置可用 LLM

但 design 又说 Anchor 阶段 2 才实现,阶段 1 不存在。这不是做事顺序问题,而是需求条件与系统能力模型矛盾。如果 Anchor 不存在,却要求完整 Anchor 才能生成章节,那么阶段 1 的 Director checkPrerequisites() 就无法合理实现。

**建议改法**: D5 应该拆成能力级别:

```
基础生成前置:
- ≥1 个主角实体
- ≥1 条世界观规则
- LLM 可用

开启 Anchor 严格校验时:
- L1 角色必须有完整 Anchor
```

也就是说,Anchor 是增强一致性的条件,不应该成为基础章节生成的硬门槛。

---

### 9. 角色升级后 Anchor 处理逻辑有自相矛盾风险

D3 说角色 L2→L1 后只更新 entities.level,不自动生成 Anchor 内容。但 Anchor 规则又要求:

- L1 每章必须命中 ≥1 条 vocabulary_signature
- L1 违反 anti_trait 强制重写

如果一个角色被自动升级为 L1,但 Anchor 还是空的,就会出现:

- 角色等级是 L1 但没有 vocabulary_signature
- Anchor 校验无法执行

requirements 后面虽然说"档案补全前按 L3 处理",但这又会和 entities.level=L1 冲突。

**建议改法**: 角色等级和 Anchor 完整度要分离。不要只看 entity.level,应该增加:

```
anchorStatus: 'missing' | 'partial' | 'complete'
anchorStrictEnabled: boolean
```

Anchor 校验依据应是: `if entity.level === 'L1' && anchorStatus === 'complete'`,而不是只看 L1/L2/L3。

### 10. Critic 的"局部重写"缺少可执行的数据结构

Critic 设计里有:

- 60-79 分请求 Writer 局部重写
- <60 分请求整章重写

tasks 也要求 Critic 决策结果通过总线发布,触发 Writer 局部或整章重写。但文档没有定义"局部重写"的定位结构。

局部重写至少要知道:

- 改哪一段?
- 原文范围是什么?
- 目标是什么?
- 改完后 CHANGES 是否重算?
- 是否影响快照?

如果没有这些字段,Writer 无法稳定执行局部改写。

**建议改法**: 定义 RewriteRequest:

```typescript
type RewriteRequest = {
  mode: 'partial' | 'full'
  targetRanges?: Array<{
    startOffset: number
    endOffset: number
    reason: string
    instruction: string
  }>
  preserveChanges: boolean
  mustReparseChanges: boolean
}
```

而且只要正文被局部改写,CHANGES 必须重新校验,否则正文和状态变更可能不一致。

---

### 11. Critic 评分 JSON 没有 Schema 约束

Critic 要用 LLM 输出 4 维评分,并解析 JSON。tasks 里只提到处理 markdown code block 包裹。但没有定义严格 schema,会导致:

```json
{ "节奏": "不错", "逻辑": 80 }
```

或者字段名中英文混用、分数超出范围、缺失 suggestions 等。

**建议改法**: 必须定义 Zod Schema:

```typescript
const CriticResultSchema = z.object({
  scores: z.object({
    pacing: z.number().min(0).max(100),
    logic: z.number().min(0).max(100),
    prose: z.number().min(0).max(100),
    satisfaction: z.number().min(0).max(100),
  }),
  decision: z.enum(['pass', 'partial_rewrite', 'full_rewrite']),
  issues: z.array(z.object({
    dimension: z.string(),
    severity: z.enum(['low', 'medium', 'high']),
    location: z.string().optional(),
    suggestion: z.string()
  }))
})
```

否则 Critic 会成为高频不稳定点。

### 12. Memory Pack 的 token 预算缺少统一算法入口

requirements 里说 Memory 数据包超过模型 context 80% 时智能裁剪,优先保留 L1+L3,L5 减半,L4 摘要化。但设计里没有明确:

- 怎么知道当前模型 context?
- 怎么估算 token?
- 不同协议蓝图怎么提供 context length?
- Writer、Critic、Humanizer 是否共享预算?

这会导致 Memory Pack 可能构建得过大,最终 LLM 请求失败。

**建议改法**: 需要统一 TokenBudgetService:

```typescript
TokenBudgetService {
  getModelContextLimit(modelId, protocol)
  estimateTokens(text)
  allocateBudget({
    systemPrompt,
    memoryPack,
    blueprint,
    outputTarget
  })
}
```

Memory 不应该自己决定全部预算,应该由调用方告诉它:

```typescript
buildMemoryPack(projectId, {
  maxTokens: 12000,
  preserve: ['L1', 'L3']
})
```

### 13. Humanizer 的 AI 率指标技术上不可验证

requirements 把目标写成"AI 率 ≤ 30%",Humanizer 还要接 GPTZero API,失败后 5 轮重试。

技术问题是:

- AI 检测器结果不可稳定复现
- 同一文本在不同检测器上差异很大
- "AI 率"不是一个可靠工程指标
- GPTZero 失败时"直接通过"会让验收目标失效

**建议改法**: 把技术指标拆成两类:

- detectorScore: 外部检测器参考分
- naturalnessMetrics: 本地可计算指标

例如:

```typescript
humanizeMetrics {
  detectorProvider
  detectorScore
  repetitionRate
  sentenceLengthVariance
  bannedPhraseHits
  paragraphRhythmScore
}
```

外部检测器只能作为参考,不能作为唯一通过条件。

### 14. 客户端全本地 Agent + 长任务运行可靠性不足

技术约束要求所有 Agent 跑在客户端,不引入服务端 Worker。但同时需求又包含:

- Auto-Pilot 连续生成 N 章
- 单章最多 600 秒
- 任务恢复
- 流式输出
- 多 Agent 重写
- 大量 LLM 调用

纯浏览器环境下会遇到:

- 页面休眠
- 标签页被浏览器降频
- 网络中断
- 电脑睡眠
- 刷新导致 AbortSignal 丢失

**建议改法**: 如果坚持无服务端,至少要区分:

```
RuntimeMode = 'browser' | 'tauri'
```

在 Tauri 模式下,长任务尽量放到 Tauri sidecar / Rust command 管理。在 browser 模式下,限制 Auto-Pilot 能力,并把恢复做得更保守。

### 15. 协议蓝图对流式能力的抽象可能不够

Writer 必须使用流式接口。design 里 Writer 直接调用 streamChatCompletion()。但 HANDOFF 里说明系统支持 OpenAI、Anthropic、Gemini、Ollama、Responses API 等多协议。不同协议的流式格式差异很大:

- OpenAI: delta.content
- Anthropic: content_block_delta
- Gemini: candidates[].content.parts
- Responses API: response.output_text.delta
- Ollama: response

如果协议蓝图没有统一 StreamAdapter,Writer 会被协议细节污染。

**建议改法**: 协议层应该提供统一事件:

```typescript
type StreamEvent =
  | { type: 'text_delta'; text: string }
  | { type: 'usage'; usage: TokenUsage }
  | { type: 'done' }
  | { type: 'error'; error: ProtocolError }
```

Writer 只消费 text_delta,不要直接理解各协议响应格式。

### 16. prompt_overrides 缺少版本管理和变量校验

专家模式允许用户修改 Agent system prompt,并保存到 prompt_overrides。问题是 prompt 一旦改坏,Agent 可能长期不可用。当前 schema 只有:

- projectId
- agentName
- promptTemplate
- updatedAt

缺少版本、是否启用、变量校验结果、回滚能力。

**建议改法**: 改成:

```
promptOverrides {
  id
  projectId
  agentName
  version
  promptTemplate
  isActive
  validationErrors
  createdAt
  updatedAt
}
```

保存前校验模板变量: `validatePromptVars(prompt, allowedVars)`,并保留最近 N 个版本,支持一键回滚。

### 17. 任务取消设计不完整

requirements 要求用户取消时,运行中的 Agent 在下一个检查点退出,流式可立即中断。但设计里 AgentContext 只有 abortSignal,没有说明:

- LLM 请求如何真正 abort?
- streamChatCompletion 是否接收 signal?
- 非流式请求取消后结果回来怎么办?
- 取消状态如何防止落库?

**建议改法**: 所有 Agent 落库前都必须检查:

```typescript
await assertTaskNotCancelled(taskId)
```

LLM 调用必须传 `fetch(url, { signal: ctx.abortSignal })`。非流式请求即使无法中断,返回后也必须丢弃结果:

```typescript
if (await isCancelled(taskId)) return
```

否则用户点击取消后,结果仍可能写入数据库。

---

### 18. Auto-Pilot 的 token 成本控制缺少跨任务累计来源

requirements 有 E_BUDGET_EXCEEDED,也要求 token 超额暂停。但 schema 只在 agentTasks.metrics 里存 tokens。没有单独的 session budget 表。问题是 Auto-Pilot 要统计跨多章、跨多个子任务的累计 token,如果只从每个 task 的 JSON metrics 临时汇总,容易慢,也容易漏。

**建议改法**: 增加:

```
budgetSessions {
  id
  projectId
  mode: 'chapter' | 'autopilot'
  tokenUsed
  maxTokens
  startedAt
  endedAt
  status
}
```

每次 LLM 调用后原子累加。否则预算控制会变成 UI 层估算,不可靠。
